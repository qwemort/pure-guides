CORS with cookies: why Access-Control-Allow-Origin: * fails, and how to fix it

Last updated: 30 October 2026 · about 5 minutes to read

Disclosure: I build PureHeaders, which is mentioned near the end as a way to fix this in local development. The explanation and the server fix work with any tool.
Short version
  1. If the request sends cookies (credentials: "include" or withCredentials = true), the server must answer with the exact origin, not *.
  2. It must also send Access-Control-Allow-Credentials: true and Vary: Origin.
  3. If the browser sends a preflight (OPTIONS), that request needs a 2xx answer and the right Allow-Methods and Allow-Headers, and these cannot be * either.
  4. Fix it on the server for production. For local work, you can add the headers in the browser.

The error

In the console you will see something like:

The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'.

The reason is a safety rule. A wildcard says "any website may read this response". If cookies are attached, that would let any website you visit read pages from the site where you are logged in. So the browser demands that the server names the one origin it trusts.

What a request with cookies needs

Suppose your frontend runs on http://localhost:3000 and calls https://api.example.com with cookies. The response must contain:

HeaderValueWhy
Access-Control-Allow-Originhttp://localhost:3000The exact origin of the page. No *, no trailing slash, scheme and port included.
Access-Control-Allow-CredentialstrueTells the browser the page may read a response to a request with cookies.
VaryOriginStops caches from serving one origin's answer to another origin.

If your server allows several origins, check the incoming Origin header against an allow-list and echo it back only when it matches. Do not echo any origin you receive.

The preflight people forget

The browser sends an OPTIONS request first (a "preflight") when the real request is not "simple". That happens, for example, when you send a custom header such as Authorization, a Content-Type of application/json, or a method like PUT or DELETE. The preflight carries no cookies, and your server has to answer it correctly:

  • The status must be 2xx. A 404, 405 or a redirect on OPTIONS fails the check, even if the real endpoint works.
  • Access-Control-Allow-Methods lists the methods you use.
  • Access-Control-Allow-Headers lists the request headers you send (for example Authorization, Content-Type).
  • For requests with credentials, a * in Allow-Methods, Allow-Headers or Expose-Headers is treated as a plain character, not a wildcard. List the names.

Why it works in Postman: Postman is not a browser and does not enforce CORS. It tells you the server answers, not that a browser will accept the answer.

The server fix

Node with Express and the cors package:

app.use(cors({
  origin: "http://localhost:3000",
  credentials: true,
  allowedHeaders: ["Authorization", "Content-Type"],
  methods: ["GET", "POST", "PUT", "DELETE"]
}));

Without a library, the idea is the same in any language: answer OPTIONS with 204, and on every response set the three headers from the table above for origins in your allow-list.

When the cookie still does not arrive

CORS can be correct and the cookie can still be missing. Check these:

  1. SameSite. localhost:3000 and api.example.com are different sites. A cookie set with SameSite=Lax or Strict is not sent on such a request. For cross-site use it needs SameSite=None; Secure.
  2. HTTPS. Secure cookies need an HTTPS API.
  3. Third-party cookie settings. The browser may block cookies that a page does not set for its own site.
  4. The client flag. fetch(url, { credentials: "include" }) or xhr.withCredentials = true. Without it the browser does not send cookies at all.
  5. Same cookie domain. The cookie must belong to the domain you call (the API), not to the page.

Open DevTools → Network, click the failing request and read the Response headers and the preflight row above it. The mistake is almost always visible there.

Local development without touching the server

You do not always control the API. A dev proxy (for example the proxy option of your dev server) removes CORS entirely, because the browser talks to your own origin. If you cannot add a proxy, a header extension can add the missing response headers for the pages and sites you choose.

PureHeaders' Fix CORS does that for one page → the API sites you list: it sends the exact origin instead of * and adds Access-Control-Allow-Credentials: true, so requests with cookies can be read. It handles methods and your custom headers too. Other websites get nothing.

PureHeaders is in the Chrome Web Store, Microsoft Edge Add-ons and Firefox Add-ons.

Honest limits: an extension changes what your browser sees, so it is a development tool, not a production fix. It cannot change a server's status code: if the server answers the preflight with an error such as 404 or 405, the browser still blocks the request and the server has to allow OPTIONS. Cookies can also still be dropped by the SameSite rules above.

Questions

Why does CORS reject * when I send cookies?
Because a wildcard would let any site read responses to requests that carry your login. The server must name the exact origin and send Access-Control-Allow-Credentials: true.

Does the Authorization header count as credentials?
Not for the credentials flag, which covers cookies, HTTP authentication and client certificates and is set with credentials: "include" or withCredentials. A custom Authorization header makes the request non-simple, so the browser sends a preflight and the server must list Authorization in Access-Control-Allow-Headers.

Why does the preflight fail even though the API works in Postman?
Postman does not enforce CORS. The browser needs a 2xx answer to OPTIONS with the right Allow-* headers; a 404, 405 or redirect fails it.

Can a browser extension fix a server-side CORS error?
In local development, yes: it can add the missing response headers. It cannot fix a server that answers OPTIONS with an error, and it is not a production fix.
